# Интеграция с приложением Mama Roma

Отдельный контур внутри плагина. Работа с Reservly не затронута: свой таймер,
свой клиент, свой секрет. Секция выключена — ни одна строчка этого кода
не исполняется. Если точка нужна только для Mama Roma, старый контур можно
выключить глобально через `reservlyEnabled: false`.

## Что где лежит

```
src/Reservly.IikoFrontBridge/MamaRoma/
├── MamaRomaConfig.cs      настройки и флаги
├── MamaRomaPayloads.cs    что уходит и что приходит
├── MamaRomaClient.cs      HTTP: забрать заказы, отправить стоп-лист и меню
├── DeliveryWriter.cs      создание доставки в iiko через editSession
├── MamaRomaCollectors.cs  стоп-лист, меню, статусы заказов
└── MamaRomaWorker.cs      свой таймер и порядок шагов
```

В существующих файлах минимум склейки: поле конфига, `using`, создание работника
в конструкторе, освобождение в `Dispose`, плюс общий флаг Reservly.

## Как включить

В `bridge.settings.json` секция `mamaroma`. По умолчанию `enabled: false` —
плагин ведёт себя ровно как раньше. Top-level `reservlyEnabled: false`
выключает только отправку в Reservly и не отключает Mama Roma.

```json
"mamaroma": {
  "enabled": true,
  "backendUrl": "https://api.mamaroma.ru/api/v1/integrations/iiko",
  "secret": "общий секрет, свой у каждой сети",
  "restaurantId": "UUID ресторана из таблицы restaurants",

  "acceptDeliveries": true,
  "deliveryPollIntervalSeconds": 20,
  "deliveryOrderTypeId": "",
  "pickupOrderTypeId": "",
  "marketingSourceId": "",
  "deliveryOrderTypeName": "",
  "pickupOrderTypeName": "",
  "cutleryProductId": "",
  "cutleryProductSizeId": "",
  "cutleryProductName": "Приборы",
  "missingProductFallbackProductId": "",
  "missingProductFallbackProductSizeId": "",
  "missingProductFallbackProductName": "Аварийная позиция",
  "defaultDeliveryMinutes": 60,
  "deliveryBatchSize": 10,

  "syncStopList": true,
  "stopListIntervalMinutes": 1,
  "stopOnRemainingAmount": true,
  "remainingAmountThreshold": 0,

  "syncMenu": true,
  "menuIntervalMinutes": 360,
  "menuSchemaVersion": "mamaroma-menu-v2",
  "menuIncludeInactive": false,

  "syncDeliveryStatus": true,
  "deliveryStatusIntervalSeconds": 30,
  "deliveryStatusLookbackHours": 12
}
```

`restaurantId` и `secret` свои на каждом терминале: и то и другое выдаётся
в админке приложения, раздел **Касса → Плагины**, кнопка «Выдать ключ».
Секрет показывается один раз.

**База iiko у каждого ресторана своя**, поэтому коды товаров у точек разные.
Сопоставление блюд ведётся отдельно для каждой точки — там же в админке,
раздел **Касса → Сопоставление**. Пока блюдо не сопоставлено, заказ с ним
на кассу не уедет, и это будет видно в разделе **Очередь**.

### Про порог остатка

В iiko «поставить в стоп-лист» и «выставить остаток» — разные действия,
и продажу запрещает только первое.

| Настройка | Поведение |
|---|---|
| `stopOnRemainingAmount: false` | Прячем только то, что формально в стоп-листе |
| `true`, порог `0` | Плюс то, где не осталось ни порции |
| `true`, порог `5` | Прячем заранее: последние 5 порций уйдут в зал, а не в доставку |

Сервер получает и решение (`isStopped`), и основание (`reason`), и сырые данные —
видно, почему блюдо скрыто.

## Как заказ выглядит в iiko

Видимый внешний номер заказа — `Мобильное <номер приложения>`, например
`Мобильное 260827-4529`. Технический UUID заказа приложения в это поле больше
не пишется: он хранится скрыто в external data с ключом `mamaroma.orderId`.
По нему плагин потом узнаёт свои доставки и не создаёт дубли.

Источник заказа (`OrderOriginName`) ставится как `Мобильное`. Если в настройках
задан `marketingSourceId`, дополнительно проставляется маркетинговый источник
iiko для отчётов.

Комментарий к доставке собирается строго в таком порядке:

1. Оплата: `Оплата картой`, `Наличные`, `Наличные с 5000 руб`,
   `Оплачено в приложении` или `Оплачено в приложении: СБП`.
2. Комментарий гостя из корзины.
3. Комментарий к сохранённому адресу, например `Вход со двора`.
4. Предупреждение об аварийной позиции, если она была использована.

Полный адрес в комментарий к доставке не дублируется.

Адресные поля заполняются по своим окнам iiko:

| Поле приложения | Поле iiko |
|---|---|
| Город/улица/дом/корпус/строение | `Line1`, а в старом формате ещё `StreetId`, `House`, `Building` |
| Квартира | `Flat` |
| Подъезд | `Entrance` |
| Этаж | `Floor` |
| Домофон | `Doorphone` |

`Line2` в обычном заказе не заполняется, чтобы не захламлять карточку доставки.
Туда попадёт только аварийная подсказка, если одно из отдельных адресных полей
оказалось длиннее лимита iiko и было обрезано перед записью в своё окно.

Поле `AdditionalInfo` используется как «Примечания»: туда пишется
`Мобильное приложение`, а также списанные/начисленные баллы и скидка, если они
есть. Например:
`Мобильное приложение. Списано баллов: 300. Начислено баллов: 50. Скидка: 10 руб по промокоду LETO`.

Про деньги: касса считает свою цену по прайсу, поэтому наш итог, скидки,
сдача и баллы уходят отдельными полями и попадают в понятные текстовые места
iiko. Расхождение должно быть видно кассиру сразу, а не всплыть при вручении.

Платные приборы добавляются в iiko отдельной позицией из `cutleryProductId`
с количеством `personsCount`. Цена задаётся из заказа приложения:
`cutleryKopecks / personsCount` — сейчас 30 ₽ за комплект. Если товар
приборов не задан или не найден, применяется тот же аварийный сценарий, что
для блюд. Если аварийный товар не настроен, заказ не заводится без этой
платной строки и уходит в очередь с ошибкой.

### Аварийная позиция

Основной режим — блюда и добавки должны быть сопоставлены с товарами iiko
в админке. Но на случай, если связь забыли, товар удалили или код оказался
неверным, есть запасной механизм.

Если `missingProductFallbackProductId` пустой, поведение строгое: заказ с
несопоставленной позицией не создаётся, а в `missingProducts` возвращается
список проблемных блюд.

Если `missingProductFallbackProductId` задан и этот товар найден в iiko, заказ
создаётся. Вместо проблемной позиции добавляется аварийный товар с ценой `0`,
кастомным именем `НЕ НАЙДЕНО: <исходное блюдо>` и комментарием к позиции:
`Аварийная замена ... Нужно вручную заменить на: <исходное блюдо>`.

Общий комментарий к доставке тоже получает предупреждение:
`ВНИМАНИЕ: не найдены позиции, добавлен аварийный товар: ...`.
В `POST /orders/ack` такой заказ приходит как `accepted`, но `error` и
`missingProducts` не очищаются — в админке остаётся след, что заказ прошёл
через аварийную замену.

Заказ, уже заведённый в кассе, второй раз не заводится: плагин ищет доставку
по скрытому `mamaroma.orderId`, старому UUID во внешнем номере или новому
виду `Мобильное <номер>`, и возвращает прежний результат. Отчёт, не дошедший
из-за связи, ложится в очередь на диск (`mamaroma-ack-queue`) и уходит на
следующем круге.

Сервер может отдать заказ повторно, если подтверждение не дошло после таймаута.
Плагин всё равно заведёт его один раз: перед созданием он ищет уже заведённую
доставку. На стороне сервера заказ, отданный плагину, закрывается замком на
3 минуты (`LOCK_MINUTES = 3`), чтобы два опроса подряд не забрали один и тот
же заказ.

### `POST /orders/ack`

Чем закончилось. Приходит **всегда**, в том числе при неудаче.

```json
{ "restaurantId": "…", "results": [
  { "orderId": "…", "status": "accepted",
    "iikoOrderId": "…", "iikoOrderNumber": "512",
    "error": "", "missingProducts": [], "reportedAt": "…" },
  { "orderId": "…", "status": "failed",
    "error": "Не найдены товары: Пепперони (8f2a…)",
    "missingProducts": ["Пепперони (8f2a…)"] }
] }
```

`status: failed` и непустой `missingProducts` — сопоставление блюд разъехалось,
заказ не уехал на кухню, гость ждёт.

`status: accepted`, но `error`/`missingProducts` непустые — заказ создан через
аварийный товар. Менеджер видит это в iiko, а админка сохраняет предупреждение,
чтобы потом исправить сопоставление.

### `POST /stop-list`

```json
{ "restaurantId": "…", "capturedAt": "…",
  "stopOnRemainingAmount": true, "remainingAmountThreshold": 0,
  "items": [ {
    "productId": "…", "productName": "Карбонара", "sizeId": "",
    "remainingAmount": 0, "isRestricted": true,
    "isStopped": true, "reason": "restricted"
  } ] }
```

Приходит только при изменениях. Полный список того, что сейчас в стопе, —
позиции, которых нет в массиве, снова доступны.

### `POST /menu`

Номенклатура точки: `productId`, `name`, `code`, `groupName`, `groupPath`,
`category`, `measureUnit`, `isActive`, `hasSizes`. Нужна для сопоставления
блюд приложения с товарами iiko.

`hasSizes: true` — в заказе для этого товара обязателен `sizeId`.

`menuSchemaVersion` входит во внутренний hash выгрузки. Если в плагин добавили
новые поля меню, поднимите значение — после перезапуска терминал отправит
полный срез заново.

### `POST /delivery-status`

Состояние заказов, заведённых через нас. Новые заказы узнаём по скрытому
`mamaroma.orderId`; старые — по внешнему номеру, который раньше был UUID,
или по новому виду `Мобильное <номер приложения>`.

```json
{ "restaurantId": "…", "orders": [ {
  "orderId": "наш UUID", "iikoOrderNumber": "512", "status": "OnWay",
  "confirmedAt": "…", "printedAt": "…", "cookingFinishedAt": "…",
  "sentAt": "…", "deliveredAt": "…", "cancelledAt": "",
  "predictedCookingCompleteAt": "…",
  "hasProblem": false, "problemComment": "", "cancelComment": "",
  "courierName": "Иван",
  "items": [
    {"productId": "UUID", "name": "Пицца Маргарита (ДОСТ)", "amount": 1}
  ]
} ] }
```

**Этапы для гостя считаются по меткам, а не по статусу** — на V8 «готовим»
и «готово» иначе не получить:

| Этап у гостя | Признак |
|---|---|
| Принят | `confirmedAt` заполнено |
| Готовим | `printedAt` заполнено — позиции ушли на кухню |
| Готов / в пути | `cookingFinishedAt` или `sentAt` |
| Доставлен | `deliveredAt` |

`hasProblem` — отдельный случай: на кухне отметили проблему. Об этом стоит
узнать раньше гостя.

В status-срезе также приходит фактический состав заказа из iiko. Если менеджер
удалил, заменил или обнулил позицию на кассе, сервер сохраняет `iiko_items` и
ставит `iiko_items_changed_at`. Приложение показывает гостю, что состав заказа
изменился; если в iiko удалили всё, приложение видит пустой список.

## Про типы заказов

Списка типов заказов iikoFront V8 через API **не отдаёт вообще** — есть только
поиск по коду. Поэтому:

1. Если в настройках задан `deliveryOrderTypeId` / `pickupOrderTypeId` — берём его.
2. Иначе смотрим на уже заведённые доставки этой точки и берём тип оттуда:
   сначала по названию из `deliveryOrderTypeName`, потом по способу
   обслуживания (курьером или самовывоз).
3. Ничего не нашли — заказ не заводится, в очереди будет видно причину.

То же с источником заказа: список не отдаётся, только `marketingSourceId`.

## Сверка с SDK

Все вызовы сверены с `Resto.Front.Api.V8` 8.7.6032 — сигнатуры взяты из самого
пакета, а не из документации. Что оказалось не так, как в примерах в сети:

| Вызов | Как на самом деле |
|---|---|
| `SubmitChanges` | Вторым аргументом обязательны учётные данные: `GetDefaultCredentials()` |
| `AddOrderModifierItem` | `(amount, modifier, group, order, item, payableAmount, price)`, количество целое |
| `ChangeDeliveryMarketingSource` | Принимает сущность источника, а не строку, и первым аргументом идёт заказ |
| `GetDeliveryOrders` | Требует аргумент: включать ли удалённые |
| `GetActiveProducts` | Такого метода нет — только `GetAllProducts()` с фильтром по `IsActive` |
| Размер по умолчанию | Живёт у шкалы товара (`Scale.DefaultSize`), у самого товара его нет |
| `OrderServiceTypes`, `IOrderType` | Лежат в `Resto.Front.Api.Data.Organization` |

## Порядок обкатки

1. Для точки Mama Roma поставить `reservlyEnabled: false`, чтобы старый
   контур Reservly вообще не отправлял данные
2. `mamaroma.enabled: true`, но `acceptDeliveries: false` — только чтение: стоп-лист,
   меню, статусы. **Ничего не пишется в iiko**
3. Сопоставить блюда по выгруженному меню
4. `acceptDeliveries: true` на **одном** терминале, один тестовый заказ
5. Раскатка на остальные точки

Второй шаг стоит подержать неделю: он полезен сам по себе и ничего не может
сломать у клиента.
